# An iteration has a policy phase and an execution phase; the Policymaker decides how many passes the first needs

Before, a Policymaker session opened an iteration, ended, and the work it ordered (an audit, evaluator maintenance) ran beside the shaper's tasks. Nothing read the results of those orders until a trigger happened to fire in a later iteration, and some outcomes (an evaluator order ending `inconclusive`) had no trigger at all. The shaper planned without the findings the Policymaker had just ordered.

Now an iteration has two phases. In the policy phase the Policymaker runs, may change managed definitions and may order policy-layer work. When every session it ordered has ended, in any status, the same Policymaker issue runs again on the same branch and reads the results. A pass that orders no policy-layer work ends the phase; the execution phase (the shaper and the implementation-layer orders) then runs on the organization the policy phase produced. An iteration with no due trigger has no policy phase.

The resume gives a clean agent context, not the old conversation. Continuity lives in files the Policymaker can reread (working memory, the repository, `policy_pass` in the loop state), so a resumed pass has the same footing as a first one and no hidden state decides what it knows. Everything reuses the existing relaunch of a session on the same issue and branch; the wait is driven by the end of the ordered sessions, not by a clock, and the watchdog and age limit cover it like any other wait. A session with many passes is still one session for the rollback after two failed ones.

Per pass the Policymaker chooses when its changes take effect: before the ordered sessions start (default), or, with `"merge": "later"`, together with a later pass or at the end of the phase. Its changes are in `direct_paths`, so they do not meet the change gate, and it cannot write the evaluator.

The engine does not cap the number of passes. The Policymaker has more influence on reaching the goal than any other agent, and a number chosen in advance would override its judgment in exactly the case where the goal needs more rounds. We rejected a hard cap for that reason. A cap also makes a failure silent: a phase cut off at pass N leaves the Policymaker's last orders unread, the problem the phases exist to remove. The cost of a long phase is made visible instead: after `policy_passes_notice` passes (engine default 10, `null` or 0 turns it off) the engine opens one `notice` owner request per iteration. It is informational and nothing waits on it, so a request meant for the owner cannot become what stalls the loop. Whether the Policymaker pursues the goal rather than improving its environment is a separate question (#176); if it turns out to need a guardrail, that is where one is designed.

The iteration record states the number of policy passes and, per order, the pass that placed it. The audit trigger counts an audit the Policymaker ordered and read in this iteration as seen, so the next iteration does not call it for the same report.

Supersedes the model in which the Policymaker's orders ran in the same iteration beside the shaper and its changes took effect at the next iteration boundary.
