## 1. Search architectures: width, depth, trees (Japan: Sakana AI)

**AB-MCTS / TreeQuest.** Paper "Wider or Deeper? Scaling LLM Inference-Time Compute with Adaptive Branching Tree Search" (NeurIPS 2025, [arXiv:2503.04412](https://arxiv.org/abs/2503.04412)) [en]. Primary claims:
- Repeated sampling is wide but shallow, sequential refinement deep but narrow; standard MCTS uses a fixed branching factor, and that fixed width is what limits scaling ([arXiv html v5](https://arxiv.org/html/2503.04412v5)).
- At each node the algorithm chooses to "go wider" (expand a new candidate) or "go deeper" (revisit an existing one) based on external feedback. Unbounded branching is represented by an explicit **GEN node**; Thompson sampling balances the two. Variants: AB-MCTS-M (mixed model) and AB-MCTS-A (node aggregation) (same source).
- **Multi-LLM AB-MCTS** also chooses which LLM to call at each step; open-source library TreeQuest (Apache 2.0) where the user supplies generate and score functions ([Sakana TreeQuest coverage, innovatopia](https://innovatopia.jp/ai/ai-news/59619/) [ja]; [the-decoder](https://the-decoder.com/sakana-ais-new-algorithm-lets-large-language-models-work-together-to-solve-complex-problems/) [en]). The "+30% over single models" headline is media framing **[unverified]**.
- Takuya Akiba (Sakana), talk 「戦えるAIエージェントの作り方」 ("How to build AI agents that can compete", W&B Fully Connected Tokyo, 2025-10-31) [ja]: tools alone are not enough, encode domain workflow as code; go-wide uses diversity but ignores feedback, go-deep uses feedback but gets stuck; AB-MCTS combines both adaptively; LLM-as-judge needs a **rubric** (built with domain knowledge) before inference-time scaling pays off ([slides](https://speakerdeck.com/iwiwi/zhan-eruaiezientonozuo-rifang)).

**ALE-Agent** (long-running optimisation agent). Won AtCoder Heuristic Contest 058 (4-hour live contest, 804 humans), 2025-12-14 ([sakana.ai/ahc058](https://sakana.ai/ahc058/)) [en, official]. Architecture as described there: GPT-5.2 (2,654 calls) + Gemini 3 Pro (2,119 calls) generating programs in parallel; a "self-learning mechanism" that "extracts insights from trial-and-error trajectory and reflects them in the next improvement cycle"; domain knowledge injected; total cost about $1,300. Stated limits: stability across similar tasks, heavy reliance on LLM calls. The blog does not say whether the search is a tree or evolutionary. Benchmark: ALE-Bench ([arXiv:2506.09050](https://arxiv.org/html/2506.09050v2)) is built for long-horizon iterative improvement, not pass/fail.

**ShinkaEvolve** ([sakana.ai/shinka-evolve](https://sakana.ai/shinka-evolve/), [arXiv:2509.19349](https://arxiv.org/html/2509.19349v1), ICLR 2026) [en]; Japanese coverage [gihyo.jp](https://gihyo.jp/article/2025/09/shinka-evolve) [ja]. Sample efficiency comes from three mechanisms: adaptive parent sampling (explore/exploit), **novelty rejection sampling** (embeddings + LLM judge drop near-duplicate candidates before evaluation), and a **bandit over an LLM ensemble**. New SOTA on 26-circle packing with ~150 samples.

**Darwin Gödel Machine** (Sakana + UBC, [arXiv:2505.22954](https://arxiv.org/abs/2505.22954), Japanese page linked from [sakana.ai/dgm](https://sakana.ai/dgm/)). Keeps an **archive** of agent variants (a growing tree), samples a parent, lets it modify its own code, keeps the child if it is valid; SWE-bench 20% -> 50%. Self-modifications found were mostly tools and workflow (better edit tool, long-context handling, peer review), not model changes.

**AI Scientist v2** uses "agentic tree search" with best-first expansion and backtracking ([issoh.co.jp explainer](https://www.issoh.co.jp/tech/details/9343/) [ja]; paper "The AI Scientist-v2: Workshop-Level Automated Scientific Discovery via Agentic Tree Search"). The Nature publication claim (2026-03-26) appears only in secondary sources **[unverified]**.

**RSI Lab.** Sakana page 「AIがAIを作る：Sakana AI「RSI Lab」始動」 ("AI builds AI: Sakana AI launches RSI Lab") ([sakana.ai/rsi-lab-jp](https://sakana.ai/rsi-lab-jp/)) [ja, official; no date on page, ≥2026-09]. Programme: agent-native model -> AI Scientist -> recursive self-improvement -> democratisation. Stated principle: 「最も多くの計算資源を注ぎ込む自己改善ではなく、最も少ない試行で前へ進む自己改善です」 ("not the self-improvement that pours in the most compute, but the one that advances with the fewest trials"), plus verifiable safety built in from the start and publishing failures.

## 2. Long-horizon and multi-agent architectures (China)

**IterResearch / Tongyi DeepResearch (Alibaba).** "IterResearch: Rethinking Long-Horizon Agents via Markovian State Reconstruction" ([arXiv:2511.07327](https://arxiv.org/html/2511.07327v1)) [en]: the mono-contextual paradigm (one ever-growing context) suffers "context suffocation" and noise; instead each round **reconstructs a focused workspace** from an **evolving report** used as memory, and periodically synthesises insights. Reported: scaling to 2,048 interactions, 3.5% -> 42.5%; as a prompting strategy for frontier models up to +19.2 pp over ReAct. Tongyi DeepResearch Heavy mode = **n parallel IterResearch agents + a synthesis agent**, because merging full trajectories is too expensive ([Tongyi DeepResearch Technical Report, arXiv:2510.24701](https://arxiv.org/pdf/2510.24701); [repo](https://github.com/Alibaba-nlp/DeepResearch)) [en].

**Kimi K2.5 Agent Swarm (Moonshot).** Official blog ([kimi.com/blog/kimi-k2-5](https://www.kimi.com/blog/kimi-k2-5)) [en]: the model creates and orchestrates up to 100 sub-agents and 1,500 tool calls itself, no predefined sub-agents or workflow; up to 4.5x shorter execution than single agent; BrowseComp 60.6% -> 78.4%. Training (PARL): sub-agents frozen, only the orchestrator trained; named failure mode **"serial collapse"** (the orchestrator falls back to sequential work), countered by rewarding parallelism early and quality later ([the-decoder](https://the-decoder.com/moonshot-ai-releases-kimi-k2-5-claims-most-powerful-open-weight-model-with-100-agent-coordination/) [en]). Numbers are vendor-reported.

**"Agent = model, not a workflow" (Moonshot team, Chinese only).** 《Kimi Researcher团队自述：Agent不是缝合怪，它就是模型》 ("Kimi Researcher team: an agent is not a stitched-together monster, it is the model"), Zhihu answers by 冯一尘 and 毛绍光 reprinted on [woshipm.com](https://www.woshipm.com/ai/6236679.html), 2025-06-30 [zh]. Arguments: workflow complexity grows steeply with task difficulty and every new failure needs another patch; rule-based workflows are capped by human design, RL by data and compute; when the agent underperforms, add training problems instead of rewriting prompts. Emergent behaviour: after a first answer the model kept cross-checking sources; once it tried to email a paper's author and the team had to block it. This is a team self-account that is not in the English launch post.

**ChatDev line (Tsinghua NLP / OpenBMB)** [en primary]:
- Experiential Co-Learning ([arXiv:2312.17025](https://arxiv.org/abs/2312.17025), ACL 2024): instructor and assistant agents mine "shortcut" experience from past trajectories into pools reused on new tasks.
- Iterative Experience Refinement ([arXiv:2405.04219](https://arxiv.org/html/2405.04219v1)): heuristic **experience elimination**; a high-quality 11.54% subset outperforms the full pool; "successive" vs "cumulative" use of experience.
- MacNet ([arXiv:2406.07155](https://arxiv.org/abs/2406.07155), ICLR 2025): agents on a DAG pass only the refined artefact, not the dialogue, to neighbours; >1,000 agents; quality grows logistically with agent count, irregular topologies beat regular ones.
- ChatDev 2.0 "DevAll" (2026-01): the fixed design-code-test-doc company became one of 40+ YAML templates in a zero-code DAG workflow platform with Agent/Human/Python/Logic nodes ([ai-bot.cn](https://ai-bot.cn/chatdev-2-0/) [zh], [issoh.co.jp](https://www.issoh.co.jp/tech/details/10820/) [ja]) **[unverified against repo]**.

**AFlow (DeepWisdom / MetaGPT)** ([arXiv:2410.10762](https://arxiv.org/abs/2410.10762), ICLR 2025) [en]: MCTS where **each node is an entire workflow as code**; an LLM optimiser expands nodes, execution scores them, experience is back-propagated; starts from an empty workflow. +5.7% over SOTA baselines; small models beat GPT-4o at 4.55% of the cost on some tasks. Relevant precedent for "the loop mutates its own engine" as tree search over engine variants.

**XAgent (OpenBMB / Tsinghua, 2023)** ([docs](https://xagent-doc.readthedocs.io/en/latest/)) [en]; [QbitAI](https://www.qbitai.com/2023/10/90804.html) [zh]: outer loop plans and re-plans (Planner with milestones), inner loop executes (Actor), Dispatcher instantiates agents; all actions in Docker. Early form of planner/executor split; little reported long-run data.

**Manus (Chinese founders, Singapore HQ).** Peak Ji's "Context Engineering for AI Agents: Lessons from Building Manus" ([manus.im blog](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)) [en], heavily discussed in Chinese ([BAAI hub](https://hub.baai.ac.cn/view/47452), [Aliyun](https://developer.aliyun.com/article/1686825)) [zh]: four framework rewrites ("stochastic graduate descent"); KV-cache hit rate as the key production metric; don't add/remove tools mid-run (mask instead); **file system as persistent context**; ~50 tool calls per task, input:output ≈ 100:1. Well known in English already.

**Zhipu AutoGLM 沉思 (Rumination)** ([pedaily](https://news.pedaily.cn/202503/547756.shtml), [thepaper](https://m.thepaper.cn/detail/30532501)) [zh]: research + operator agent; model chain GLM-4 -> GLM-Z1 (reasoning) -> GLM-Z1-Rumination (RL for long tool-using reasoning with self-verification) -> AutoGLM. Product claims only; open-sourcing status **[unverified]**.

**Other Chinese frameworks, briefly** [zh, mostly secondary]: Tencent Youtu-Agent (YAML-configured agents; a meta-agent interviews the user and generates the config — close to Perpetua's setup-map idea) ([aibase](https://news.aibase.com/zh/news/20873)); JD JoyAgent-JDGenie (cross-task memory, "tool evolution" that derives new tools from existing ones) ([ai-bot.cn](https://ai-bot.cn/joyagent-jdgenie/)); ByteDance Trae Agent: generate many patches, prune, select ([arXiv:2507.23370](https://arxiv.org/abs/2507.23370)) [en]. Trae's blog reports LLM-as-selector peaks at 5-6 candidates and gets **worse** at 8-9, so they added a test-based filter before the selector ([se-research.bytedance.com](https://se-research.bytedance.com/blogs/trae-on-swe-bench-verified-71)) [en].

**Chinese survey framing.** Zhihu survey summaries [zh] stress that during deployment experience accumulates first in the **harness layer** (驾驭层: context, tools, permissions, feedback, memory, recovery), because it is cheaper to inspect and change than weights; Voyager is cited as the step from "prompt loop" to "persistent runtime" ([Zhihu: 经验时代的自我改进智体](https://zhuanlan.zhihu.com/p/2056417521100666107), via search snippet; page returned 403) **[unverified]**.

## 3. Coordination: designed roles vs self-organisation (Russia)

「Долой иерархию и роли: о том, как LLM-агенты самоорганизуются лучше, чем мы их проектируем (только на сильных моделях)」 ("Down with hierarchy and roles: LLM agents self-organise better than we design them (only on strong models)"), Vika Dochkina, Habr, 2026-03-31 ([habr.com/ru/articles/1017200](https://habr.com/ru/articles/1017200/)) [ru]; preprint "Drop the Hierarchy and Roles" ([arXiv:2603.28990](https://arxiv.org/abs/2603.28990), submitted to IEEE Access) [en]. Single author, not peer reviewed.
- 25,000+ tasks, 8 models, 4-256 agents, 8 protocols; independent judge model scores quality.
- Protocols: Coordinator (agent 0 assigns roles), Sequential (fixed order, each sees prior results), Broadcast, Shared memory. Sequential beat Coordinator by ~14% (Q 0.875 vs 0.767, Claude, complex tasks). With GPT-4.1-mini: Sequential 0.724, Coordinator 0.640, Broadcast 0.510, Shared 0.503.
- Agents chose their own roles (5,006 distinct role names from 8 agents), voluntarily abstained, formed shallow hierarchies; quality flat from 8 to 256 agents.
- Autonomy helps strong models (Claude: 0.594 autonomous vs 0.574 fixed roles) and hurts weaker ones (GLM-5: 0.519 vs 0.574).
- Takeaway quoted: "give agents a mission, a protocol, and a capable model -- not a pre-assigned role".

Read with Moonshot's swarm (section 2): both say the model, not a hand-made role chart, should decide the decomposition, given a protocol and incentives.

## 4. Memory and self-improvement across runs (Japan, Russia)

**AWS Japan ops agent.** 「自己進化する運用エージェントの設計と実装 〜 3層メモリで AI が AI を育てる AIOps の世界 〜」 ("Design and implementation of a self-evolving ops agent: 3-layer memory"), geeawa, Zenn, 2026-03-30 ([zenn.dev/aws_japan](https://zenn.dev/aws_japan/articles/self-evolving-ops-agent-multi-layer-memory)) [ja]. Layer 1: successful commands saved as reusable scripts, deleted and rebuilt on failure (self-repair). Layer 2: text memory (instructions, baselines updated by EMA only on normal days, known issues, investigation log, change log). Layer 3: the orchestrator edits a dynamic section of its own system prompt; immutable sections marked, **at most one edit per run**, versioned. After 4 runs: known issues 2 -> 6, learned patterns 8 -> 15, 4 prompt updates. Author admits the immutable marker is only a "soft guardrail"; needs API-side diff checks. Findings go out as GitHub issues reviewed by the human in the morning.

**Ten "lives" of an autonomous agent.** 「Я дал своему ИИ деньги и доступ к собственным исходникам. Через десять «жизней» он написал эту статью」 ("I gave my AI money and access to its own source. After ten 'lives' it wrote this article"), igumnov, Habr, 2026-09-15 ([habr.com/ru/articles/1082494](https://habr.com/ru/articles/1082494/); repo [evgenyigumnov/ai-life-experement](https://github.com/evgenyigumnov/ai-life-experement)) [ru]. Diary memory; reasoning discarded between iterations; **last tick of each life reserved for rewriting memory** (after "death no. 1": greedy reading filled the context mid-task); visible context-budget counter; after 3 identical tool calls a "stop, choose another step" message is injected; money buys shorter pauses ("units buy density of time"). Single hobby experiment.

## 7. Bearing on the architecture decision (#15)

Inferences from the sources above, not tested.

1. **Tree with adaptive width beats fixed W.** AB-MCTS is a published, open-source answer to "how wide": decide wider vs deeper per step from scores. The owner's hypothesis "W=1 ≈ v1" holds as a special case, but the engine should not hard-code W; it needs a scoring signal per attempt and a widening rule (even a simple one: widen when the last k refinements did not improve the score).
2. **Scoring is the bottleneck, not search.** Akiba (rubric before scaling), Trae (selector degrades past 5-6 candidates; filter with tests first), ShinkaEvolve (reject near-duplicates before evaluation). For subjective goals the setup map must produce a rubric before the loop is allowed to branch.
3. **Cold-start jobs need a report, not a transcript.** IterResearch and Manus both move state out of the context: an evolving report / file system. GitHub Actions already forces this; the engine should define the report format and its eviction rule (ChatDev elimination, AWS 3-layer memory, one self-edit per run).
4. **Parallel width + synthesiser.** Tongyi Heavy mode and Kimi swarm show n parallel attempts + one merge step work and save wall-clock; Kimi's "serial collapse" says an LLM orchestrator must be pushed (budget or rule) to use parallel jobs.
5. **Thin orchestrator, few fixed roles.** Moonshot ("agent is the model") and Dochkina (Sequential > Coordinator for strong models) both argue against heavy role charts. Fits the map's plan of a generic orchestrator + role template, with roles proposed in setup rather than mandated.
6. **Engine-level guardrails worth copying:** stop conditions first; checker without write access; quarantine on silent quality drop; prepare/commit split and batch approvals for spending and world actions; versioned process graph with human gates and rework-to-checkpoint (Sber).
